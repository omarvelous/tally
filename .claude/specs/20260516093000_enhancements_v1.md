# Tally — Product Spec v2 (Delta)

> This document captures changes made to the Tally prototype since v1 (`Tally Spec.md`). Read v1 first for the product north star, task types, completion math, and screens. This delta documents new interaction patterns, screen consolidations, and additions — everything else from v1 is unchanged.

When v1 and v2 disagree, v2 wins. The interactive reference is `Tally.html`.

---

## Summary of changes

The biggest shift since v1 is the introduction of a **single modal log surface** (`LogSheet`) that replaces the full-screen task detail. Combined with **swipe-to-log** on task rows and **swipe-to-delete** on log entries, Tally became more iOS-native and one-handed: most interactions are now a swipe-and-tap away without leaving the current screen's context.

Secondary changes: the tab bar lost the "Add" entry (creation moved to a Tasks-screen button), management actions consolidated to the task stats screen, an archived-task view returned, and two new screens were added — Profile editor + Sign in/Create account.

---

## 1. New: LogSheet (modal log surface)

Replaces the v1 full-screen TaskDetail. A bottom-sheet modal that takes ~95% of screen height, opened by:
- **Today screen** — tap any task row
- **Tasks screen** — swipe left on any task row
- **Task stats screen** — header "+ LOG" button

### Structure (top to bottom)

1. **Drag handle** + **title row**: task name on the left, schedule meta + status pill on a second line below, `CLOSE` button on the right.
2. **Scrollable middle**: TaskHero (type-specific progress card) and today's log entries.
3. **Pinned footer**: TaskControls — log form, **always at the same position** regardless of how many entries exist above.

The pinned footer is the canonical fix for "the LOG button moves around when I add an entry" — the form's vertical position is now constant.

### TaskControls layout (uniform across types)

Every log form is a single column with the primary action at the bottom. All controls share **56px height** for visual rhythm.

| Type | Footer composition |
|---|---|
| **count** / **timer** | `QUICK ADD` label → 4 preset chips (set staged value) → editable input with unit → `LOG +N` button (full-width primary) |
| **numeric** | `ENTER READING` label → input → `SAVE` button (full-width primary) |
| **check** | Single `Mark complete` button (full-width primary; disabled when already done) |
| **yes/no** | `TODAY'S ANSWER` label → two equal-width buttons side by side |

### Staged-input pattern (count + timer)

Preset chips **no longer auto-commit**. Tapping a chip stages its value into the editable input field (highlighted indigo). The user must tap the **LOG** button to commit. Live preview on the button label: `LOG +25`.

Rationale: prevents fat-finger double-logs, makes the increment visible, lets the user fine-tune before committing.

## 2. New interaction: swipe-to-log

On the Tasks screen (active view), every row supports a horizontal swipe gesture. Pull a row left more than 70px to reveal a green `LOG →` pill; release to open the LogSheet for that task.

- **Tap** on the same row still goes to the task's stats screen.
- **Mid-swipe → release before threshold** snaps back, no action.
- Disabled on archived rows (no logging on dormant tasks).

Implementation: `SwipeableRow` primitive — generic gesture wrapper that locks to the X axis after a small drag, prevents click events when a swipe completes, supports both pointer and touch events.

---

## 3. New interaction: swipe-to-delete (log entries)

Inside the LogSheet, today's log entries support left-swipe-to-delete with confirmation:

1. Pull an entry left → red `DELETE` pill reveals.
2. Release past threshold → native confirm dialog: `Delete this entry? · 12:08 · +25 reps`.
3. Confirm → entry removed; cancel → no-op, row snaps back.

Tap-to-undo (the v1 behavior) is removed. Swipe is the only way to delete — intentional friction since accidentally removed log entries break streak math.

---

## 4. Tasks screen — consolidated CRUD

The Tasks screen is the single library for all task management.

### Layout

- Header: `LIBRARY · N ACTIVE · M ARCHIVED` kicker, "Tasks" title, **+ NEW** button on the right.
- **View filter chips**: `ACTIVE · N` / `ARCHIVED · M` — switches the visible list.
- **Sort chips**: `BY RATE` / `BY NAME`.
- Column header: `— · NAME · SCHEDULE · 14D · RATE`.
- Rows: status pip, name + schedule meta, 14-day sparkline, completion-rate %.
- Footer hint adapts to view: `TAP TO VIEW · SWIPE LEFT TO LOG` in active view, `TAP TO REVIEW + RESTORE` in archived view.

### Archived rows

Render at 60% opacity, gray pip (not health-colored), tap-only (no swipe). Tap routes to the task stats screen where the **Restore** action lives.

---

## 5. Task stats screen — added "MANAGE" section

The per-task stats screen gained a bottom **MANAGE** section that replaces the v1 kebab menu / action sheet:

- **Edit task** — opens the editor.
- **Archive task** / **Restore** — toggles archived state, pops back to caller.
- **Delete task** — destructive, confirms, wipes task + all log entries, pops back.

The header right slot is reserved for a quick `+ LOG` shortcut (opens the LogSheet for this task).

---

## 6. Tab bar — slimmed to 4

| v1 | v2 |
|---|---|
| Today · Tasks · Add · Streak · More | Today · Tasks · Streak · More |

The dedicated "Add" tab is gone. Task creation happens via:
- **Tasks screen** → header `+ NEW` button
- **Today screen** empty state → `+ New task` CTA

This makes Tasks the unambiguous home for creating, editing, archiving, deleting, and reviewing tasks.

---

## 7. More tab — tightened

Removed the v1 "Tasks" section (Manage tasks / Add task nav rows) since Tasks screen owns those flows now.

Added:
- **Profile card at top** (was a non-tappable display, now opens the Profile editor).
- **Preview · Auth flows** section: "Sign in / Create account", "View onboarding" (intent: let designers/reviewers see the auth screens without signing out).

The Demo · Time-travel and Data sections are unchanged.

---

## 8. New screen: Profile editor

Stack screen, reached from More → account card.

### Components

- **Avatar tile** — large indigo square with live initials.
- **Initials are auto-derived from name** until the user manually overrides them. Once overridden, that field is no longer linked.
- **Name** input — required, validated.
- **Email** input — validated (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`); inline error message in red when invalid.
- **Initials override** — 2-char uppercase, optional.
- **ACCOUNT section** — Change password, Connected accounts, Export data, Delete account (all destructive items in red).
- **Sign out** — bottom row, red text + danger button.
- **Save** in header right (disabled until form is valid).

### Data

`settings.name`, `settings.email`, `settings.initials` live alongside other settings (dark, density, icons). The avatar everywhere else in the app reads from these values, so editing them updates the More card immediately.

## 9. New screen: Sign in / Create account

Stack screen, reached from More → "Sign in / Create account" preview row. Single screen with a segmented mode toggle.

### Composition

- **Brand** — Tally wordmark + indigo "T" logo.
- **Headline + sub** that swap with mode: `Welcome back.` / `Start your streak.`
- **Mode toggle** — segmented control: `Sign in` / `Create account`.
- **SSO buttons** — Continue with Apple (black, primary on iOS), Continue with Google (outlined).
- **OR divider**.
- **Form**:
  - Name field (sign-up only)
  - Email field — validated
  - Password field with show/hide toggle, `letter-spacing: 0.2em` when masked for dot density
  - In sign-up mode: 4-segment password strength meter (length, mixed case, special)
- **Forgot password** link (sign-in only).
- **Continue / Create account** primary button — 56px tall, disabled until valid.
- **Terms + Privacy** footer (sign-up only).

No real authentication — the submit button just closes the overlay. The screen exists for visual review.

## 10. UI primitives — additions and changes

### `Sheet` (modified)
Added two new props:
- `subtitle` (ReactNode) — rendered under the title in the header block.
- `footer` (ReactNode) — pinned at the bottom of the sheet, separated from scrollable content by a hairline rule.
- `fullHeight` (was already there) — uses `calc(100% - 30px)` so the modal is always the same tall size, which makes the pinned footer feel rooted.

### `SwipeableRow` (new)
Generic horizontal-swipe wrapper. Children render normally; on swipe past 70px (with x-axis lock), `onSwipeAction()` fires. Props: `actionLabel`, `actionColor` (defaults to `c.pos` green; used `c.neg` red for deletes).

### Navigation context (`useNav`)
Added `logTaskId`, `openLog(taskId)`, `closeLog()` to the existing nav state. The LogSheet is rendered as a peer to the active screen inside `Tabs`, so it overlays anything (tabs, stack screens). Calling `openLog` from any screen surfaces the modal.

### Removed overlay route
`taskDetail` (the v1 full-screen log) is no longer routed. The `TaskDetail` component still exists in the codebase but is dead code — kept as a reference; safe to delete in a cleanup pass.

## 12. Updated open questions

In addition to v1's open questions:

1. **Archived task restoration UX** — currently restore happens via the task stats screen's MANAGE section. Should there be a one-tap restore directly on the archived row (e.g. swipe-right reveals `RESTORE`)?
2. **Log entry swipe — destructive without grace** — should the confirm dialog be inline (toast with Undo button on the deleted row) instead of a blocking native alert?
3. **Quick-log presets — task type still requires manual unit input** — should we offer presets that auto-fill based on unit (water in oz → `8 / 16 / 24 / 32`, in ml → `125 / 250 / 500 / 750`)? Currently `pickPresets` already does some of this but isn't surfaced to the user when adding a task.
4. **Profile / auth gating** — the prototype lets users move freely between auth screens and the app. Production: gate the main app behind a real auth check; route unauthenticated users to Sign in.
5. **Continue with Apple / Google** — currently visual only. Confirm which SSO providers the build will actually support before committing UI surface to them.
6. **Avatar customization** — initials are auto-derived from name today. Should we support photo uploads, accent-color picking, or emoji avatars?
